# Terraform Backend Bootstrap

This directory creates the remote state infrastructure used by the asynchronous worker stack:

- a private, encrypted, versioned S3 bucket for Terraform state;
- a DynamoDB table for state locking;
- the supporting bucket policy, ownership controls, public-access block, and SSM parameter.

It uses the following module revision:

```hcl
source = "git::ssh://git@github.com/wearetechnative/terraform-aws-module-terraform-backend.git?ref=59f17d5e6480e1347e5dd6ea83f200036e4242d8"
```

## Why this is a separate Terraform root

Terraform cannot initialize an S3 backend before its bucket exists. This configuration therefore starts with local state, creates the backend infrastructure, and then migrates its own state to S3. The application uses the same bucket with a different key.

| Configuration | State key |
| --- | --- |
| Backend bootstrap | `asynchronous-worker/backend-bootstrap.tfstate` |
| Application stack | `asynchronous-worker/terraform.tfstate` |

## Provider compatibility

The pinned backend module and its nested S3 module were built against AWS provider `4.57.0`. The bootstrap pins that exact version because AWS provider v6 rejects a null value generated by the module's optional KMS bucket-policy logic.

This constraint applies only to the bootstrap directory. The application stack can use its newer AWS provider version independently.

## 1. Create the backend infrastructure

From the repository root:

```shell
terraform -chdir=backend-bootstrap init -reconfigure
terraform -chdir=backend-bootstrap plan -out=backend.tfplan
terraform -chdir=backend-bootstrap apply backend.tfplan
```

The configured resources are:

```text
S3 bucket:      terraform-state-async-worker-lab-489947827123
DynamoDB table: terraform-state-lock-async-worker-lab-489947827123
AWS profile:    tn-playground
AWS region:     eu-central-1
```

Copy `terraform.tfvars.example` to the ignored `terraform.tfvars` file before running Terraform. Change the values in that local file, `remote-backend.tf.example`, and the root `backend.tf` together if you need different names or a different account.

## Recovering from a partial apply

Terraform records successfully created resources in `backend-bootstrap/terraform.tfstate`, even if a later resource fails. Do not delete that local state and do not manually recreate the resources.

After correcting the problem, create a fresh plan and apply it:

```shell
terraform -chdir=backend-bootstrap plan -out=backend.tfplan
terraform -chdir=backend-bootstrap apply backend.tfplan
```

A saved plan created with a different provider version should not be reused.

## 2. Migrate the bootstrap state

Only after the first apply succeeds, enable the bootstrap's remote backend:

```shell
cp backend-bootstrap/remote-backend.tf.example backend-bootstrap/remote-backend.tf
terraform -chdir=backend-bootstrap init -migrate-state
```

Confirm the migration when Terraform prompts. Once migration succeeds, the local state is no longer authoritative and can be removed.

Do not commit `remote-backend.tf` if you want account-specific backend settings to remain local. The example file is sufficient to document the expected structure.

## 3. Initialize the application

The root `backend.tf` points to the application state key. From the repository root:

```shell
terraform init -reconfigure
terraform plan -out=async-worker.tfplan
terraform apply async-worker.tfplan
```

## Destruction order

Destroy the application before the backend:

```shell
terraform destroy
terraform -chdir=backend-bootstrap destroy
```

Destroying the backend first makes the application state inaccessible. The backend bucket also has `force_destroy = false`, so it will refuse deletion while state objects remain.
